# Logistics, movement, and CPU investigation

Reviewed 2026-11-06 in the original Sushi checkout. Corrections are local; no deployment command or server Memory edit was performed.

## Findings and population verdict

**The observed live Freighter population cannot be judged from this repository alone.** No live room/creep snapshot or CPU trace was supplied or available through the connected tools. The audit found reproducible reasons for excess or ineffective capacity, but these are not proof of the particular room's live cause. Several small, distant, replacement, or remote haulers can be legitimate. Evaluate CARRY, trip time, source availability, actual progress, and delivered energy rather than headcount.

| Confirmed issue | Code evidence and correction |
| --- | --- |
| Local demand assumed full source production even when current spawning capacity/seats could not support that WORK. | `HiveMind.Economy.buildSnapshot()` previously used full `transport.creepIncome * (2 * distance + 4)`. It now bounds production by `Harvest.describe().maxAchievableWork`, retains `haul.theoreticalCarry`, and includes finite backlog recovery. A modeled 300-energy room needs **11 rather than 16 CARRY** when one source can support only two WORK. This is an attainable production target; it still anticipates useful miners, rather than requiring delivery proof before bootstrapping hauling. |
| Cached demand could reuse commitments that had already changed in the same tick. | `spawn.request.manager.getFreighterCarryDemand()` read pre-request Economy queue totals, and `requestDynamicFreightersForRoom()` trusted demand overrides. Both now read `Economy.freighterCoverage()`: active movable workers, spawning bodies, unexpired queue entries, and deduplicated accepted spawn intents. Local admission now rejects redundant CARRY, including stale queued requests. |
| Remote historical backlog and observation age could increase spawning without fresh resource evidence. | The old demand added up to 12 CARRY for backlog plus four for old sightings. `Economy.remoteHaulRequirement()` now shares production/travel/fresh-backlog math across demand, remote economics, and admission. Catch-up energy is amortized over at least a lifetime/three trips; observation age alone adds nothing. Explicit zero production stays zero. |
| Remote/transport capacity could interact incorrectly with local recovery. | Generic remote Freighter requests previously inherited the core `logistics` spending exemption. They now use `remoteMaintenance`, and admission rechecks operational remote demand. Job classification takes explicit remote/transport work before a saved local assignment. `Logistics.Jobs` temporarily borrows workers as `otherLogistics` and restores their prior assignment on completion. Workers with destroyed MOVE parts no longer cover haul capacity. |
| A partial local load could remain in collection mode after its target disappeared or emptied. | `role.Freighter.collectEnergy()` previously fell through to idle/source movement when no candidate remained, switching to delivery only when full. It now releases the pickup and delivers partial cargo. |
| All loaded haulers could select the same delivery destination, and selection repeatedly invoked pathfinding. | Old local `deliverEnergy()` called `findClosestByPath` for each priority tier every tick; remote delivery independently chose a first matching structure. Both now use `Logistics.Index.deliveryTarget()`, shared incoming energy reservations, destination priorities, and stable targets. Selection uses indexed structures/range; movement remains with Traveler/traffic. Unreachable delivery/pickup targets get a bounded retry delay and alternate work can proceed. |
| Local pickup selection favored total pile size without accounting for creep capacity/travel. | Local candidates now rank useful free-carry-limited loads per distance. Existing assignments require a 50% score improvement before retargeting. Pickup reservations continue to exclude committed energy. |
| Idle-source spreading did not actually count idle creeps. | `idleNearUsefulSource()` counted pickup assignments, but idle workers wrote none, so ties repeatedly chose the first source. `Logistics.Index` now tracks idle-source occupancy separately, with stable choices and next-tick death cleanup. |
| Optional shared-route learning could consume burst CPU while the colony exceeded its sustainable allowance. | `utility.Travel.Creep.canPlanSharedRoute()` compared usage to `tickLimit - 5`, potentially 495 CPU. It now yields at sustainable live/rolling pressure, and fatigued workers skip movement planning. Existing lanes, essential Traveler fallback, harvesting, delivery, spawning, defense, and traffic remain reachable. Economy distance refinement also defers under pressure and resumes when headroom returns. |
| CPU/utilization evidence could obscure the actual cause. | `HiveMind.Telemetry.finish()` previously subtracted the loop's initial reading from total usage. It now includes all CPU used so far. Role samples retain per-creep cost plus aggregate cost/count. Freighter utilization requires observed movement or cargo change, rather than just an assignment ID. Sampled nested movement/search/selection costs distinguish pathfinding from role decisions and traffic. |

## Existing systems retained

The shared tick index, Economy, Harvest planning, spawn Arbiter/Policy/Intents, Logistics.Index, Traveler, canonical remote routes, and traffic resolver remain the owners of their existing responsibilities. No second logistics manager, population limiter, forced recycling policy, or diagnostic suppression was added. The old displayed 50-CARRY clamp and idle adjustment were removed because they did not constrain the assignment-specific deficits actually used for spawning.

Local hauling remains independent of remote assignments. Local source distances are cached bounded paths to storage/main spawn with a range fallback. Remote routes already model terrain, loaded versus empty body movement, route safety, and observed trip times; that implementation was retained. Traffic already supports displacement, priorities, stationary mining seats, obstacles, and canonical-route sidesteps; tests did not justify replacing it.

## CPU evidence and validation

An identical ten-loaded-hauler mock was run against the actual `HEAD` Freighter role and the corrected role. Delivery selection changed from **10 path-search API calls and one selected destination to zero path-search API calls and ten selected destinations**. See `validation/logistics-benchmark.json`. This measures API calls/coordination, **not Screeps CPU milliseconds**; subsequent movement can still pathfind.

At 16 used CPU with a sustainable limit of 20 and burst ceiling of 500, a 100-tick regression performs zero optional shared searches while essential fallback is called on all 100 ticks. Fatigued creeps perform no shared search. Deferred local distance calculations refine when pressure clears, and retain the normal cache thereafter.

`npm run validate` passed all **41 commands / 599 PASS checks**, including the new `test/logistics-audit.js`; `npm run test:logistics` runs it alone. The focused suite covers 28 scenarios: excessive/insufficient capacity, unequal source distances, same-tick queue mutations, pending/spawning intent deduplication, remote/local/explicit transport separation, stale sightings, zero production, depleted pickups, partial loads, full/destroyed/unreachable deliveries, shared reservations and deaths, useful pickup scoring, failed versus resolved intents, idle occupancy, immobile workers, traffic blockers/mining locks, and sustained CPU pressure. The module graph has 107 reachable modules and no cycles; the movement audit and `git diff --check` passed.

The broader suite includes remote routing and predictive dispatch, canonical lane congestion, multiple spawns, resource policy, diagnostics, and a 900-cycle combined miner/hauler loss and recovery simulation (restored at cycle 878, 26 spawns, maximum queue four). Final results are recorded in `validation/logistics-final.log`; no live engine, account, or room performance is represented by these mocked checks.

## Live verification after a separately authorized deployment

1. Record `JSON.stringify(Sushi.debug.cpu())` and `JSON.stringify(Sushi.debug.room("W3S47"))` before changing the live version, or substitute the affected home room. Keep the source rows, local/remote required/living/queued/spawning CARRY, all Freighter jobs, positions, cargo, TTL, and spawn decision. Existing helpers can supply the initial phase/role trace even before the new fields exist.
2. After the user deploys, allow normal sampling over several full haul trips. Use `Sushi.debug.mode("PROFILE", 100)` for a bounded detailed trace, then record `Sushi.debug.cpu()` again. Normal operation samples roles/operations every 25 ticks; no need to leave PROFILE active. Compare rolling total and bucket trend over at least one creep lifetime; sustained average should remain below 20 with a stable or recovering bucket.
3. Compare top-level phases first. `planning` includes Economy, Capacity, and scheduled planning children; nested phase/operation costs overlap and must not be summed again. Inspect `roles.<role>.totalCpu`/`count`, then sampled `operations.costs.movement`, `travelerPath`, `sharedPath`, `pickupSelection`, and `deliverySelection`. `traffic` measures final resolution separately. The sample's `tick` identifies its age. The primary live CPU consumer remains unknown until this trace is collected.
4. Inspect `Sushi.debug.room(room).current.hauling`, `.sources`, and `.freighters`. Required capacity should follow attainable production and each source's distance, with independent remote capacity. `freighterFlow.picked`/`delivered` are observed positive/negative energy cargo changes, not accepted intent counts; delivery includes controlled overflow deposits. `idleTicks` means no observed movement/cargo progress, and can include legitimate fatigue/waiting. Compare deltas across trips, not lifetime totals across different creep ages.
5. Confirm depleted targets release partial loads; useful targets retain assignments; full/unreachable delivery targets redirect; idle workers spread; miners retain their seats; dead reservations disappear; queued and spawning replacements prevent duplicates. Old excess workers are allowed to finish their lives. Verify the corrected live spawn decision before attributing an idle worker to excessive demand.

## Remaining limits

- This change cannot guarantee a complete tick within 20 CPU. Essential intents and non-logistics systems may still dominate; actual phase traces determine the next optimization.
- Local trip sizing still approximates one step/tick and storage/main-spawn delivery. It does not fully model swamp fatigue, legacy slow body ratios, all extension/controller detours, or traffic delays. New ordinary Freighter bodies have adequate plain-terrain MOVE; individual MOVE/CARRY counts and actual flow are exposed for detecting exceptions. Remote terrain/body calibration remains more detailed.
- Local source output is attainable modeled production, not a delivered-income feedback controller. A temporarily absent miner can leave legitimate planned haul capacity idle; source restoration and queued miners must be considered together. Full source-side stores/links and full base storage can reduce realized output.
- Range-based destination ranking can choose the wrong side of a wall. Traveler still supplies the actual path; proven failures trigger temporary release. Dense/walled layouts and contested final tiles need live verification. Optional distance fallback can temporarily underestimate winding routes under sustained pressure.
- Delivery reservations coordinate Freighters. Foreman and resource couriers retain their own subsystem ownership, so their concurrent accepted intents can still compete for the same final capacity. Next-tick state reconciles such conflicts.
- Sampling cannot measure Memory serialization performed by the engine after the loop returns. More diagnostic fields add a bounded amount of creep Memory; verify actual Memory/CPU trends in the live colony.

Engine references: [CPU limit and burst bucket](https://docs.screeps.com/cpu-limit.html), [movement and fatigue](https://docs.screeps.com/creeps.html#Movement), and [next-tick resolution of intents](https://docs.screeps.com/game-loop.html). These support the distinction between sustainable/burst CPU, body movement capability, and accepted versus resolved actions.
