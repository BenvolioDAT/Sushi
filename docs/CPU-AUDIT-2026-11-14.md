# CPU audit - November 14, 2026

Local private server only; 100 CPU allowance. Source and executed baseline build: `59f4701b7b83691828b9caeeb5fd6e46dee6b0759ee87677a71af649c2b2de3e`. Executed release: `1a74aee1a982e0da4c6080b39d81f5575a2869fcbf5aa115fd9e484e09e149b5`, receipt at Game.time 2,243,429. The official-server folder was not modified.

## Measurement

An every-tick, heap-only wrapper reads CPU immediately after the normal main loop returns. This includes Telemetry.finish, which the existing telemetry.total samples before its own work. It excludes engine work after the user loop, including final Memory serialization, and excludes the audit recorder's own subsequent bookkeeping. No estimates from elapsed wall time are used. A spike is a sampled tick at or above 80 CPU. Fixed-cadence health snapshots and rolling EMAs are not used to calculate the table.

Baseline: 676 consecutive samples, ticks 2,242,690-2,243,365 inclusive; wrapper installed at 2,242,689. Total CPU sum 33,246.064065. Average 49.180568, maximum 96.096658, five spikes (7.396450 per 1,000 ticks). Most baseline ticks also have temporary nested function timers; the after window uses equivalent timers. Sampling is observational and adds some CPU; these numbers are not production engine totals or a controlled replay of identical game state.

Post-release: 676 consecutive samples, ticks 2,243,570-2,244,245 inclusive; wrapper installed at 2,243,569. Total CPU sum 32,151.881843. Results:

| Metric | Before | After |
| --- | ---: | ---: |
| Mean user-loop CPU | 49.1806 | 47.5620 |
| Highest sampled user-loop CPU | 96.0967 | 94.9243 |
| Ticks at or above 80 CPU | 5 / 676 | 5 / 676 |
| Spikes per 1,000 sampled ticks | 7.3964 | 7.3964 |
| Mean traffic phase CPU | 5.9674 | 5.4915 |

Observed mean CPU fell **3.29%** and traffic CPU fell **7.97%**. Spike frequency did not improve. These are modest observed gains, not proof of a 3.29% causal improvement: population, jobs, combat and remote workload vary between consecutive windows. Creep execution was essentially unchanged (15.7275 to 15.7942 CPU); planning and first-access Memory cost also varied. This release does not resolve the scaling problem or recurring high spikes. Raw sums and phase means are retained in before.json, after.json and comparison.json; summarize.js reproduces the arithmetic.

At tick 2,242,777 serialized Memory was 600,665 characters, including about 493 KB of room data. Large records include old colony planners, remote route data and same-room route caches. Nested timers show Diagnostics.begin dominates its phase while Diagnostics.finish is usually cheap. The colony has one owned room and one spawn, but its CPU includes remote workers, scouting, reservations and NPC defense. ## Changes

1. Cache decoded shared-lane geometry by complete origin/path content. Previously each shared-lane use constructed every RoomPosition again, even for another creep following the same lane or a fresh copy of the same Memory record. The bounded heap cache survives ordinary Memory parsing and falls back to decoding after eviction/reset. Live route validity and obstacle checks are unchanged.
2. Skip remote sidestep generation when a root creep's first-choice destination is vacant and legal. Previously the resolver enumerated/sorted alternates and consulted hazards before discovering that the requested tile was already usable. Blocked movement and recursive pushes still follow the complete original algorithm.

The isolated Node benchmark of a 40-step lane over 10,000 reads reduced allocations from 410,000 per round to 41 on initial cache fill and zero on warm rounds. Five baseline rounds took 31.24-37.52 ms; cached rounds took 2.57-4.90 ms. This demonstrates the eliminated work in that routine, not an equivalent whole-colony CPU reduction. Results: `validation/cpu-20261114/geometry-benchmark.json`.

A same-tick live decoding microbenchmark at 2,244,339 used the same valid 40-step lane for 200 reads. A reproduction of the original decoding loop took **8.248453 CPU**, while warm cached reads took **0.280327 CPU**. This supports the specific cache change under identical input. It ran after both bounded observation windows and is not included in their averages/peaks. This is one microbenchmark, not an empire-wide percentage claim.

## Live effectiveness checks

The separate post-release event recorder covered 500 consecutive ticks (2,243,747-2,244,246), recording 2,476 harvest, 639 transfer, 1,687 controller-upgrade, 429 repair, 1,461 pickup and 89 reservation events in visible rooms. It also saw four attack events and 15 object-destruction events; these include all actors and do not alone prove successful friendly defense. Recorder work cost 5.438079 CPU total (about 0.0109 CPU per tick), ran after the CPU observation point, and was excluded from the comparison.

At 2,244,009 local harvest was 10/10 WORK, local CARRY 23/22 required, and local idle/no-progress haulers were both zero. Five Artificers were performing repair or controller fallback. No build events occurred in this 500-tick window; live construction effectiveness is therefore not certified, although the existing construction/movement regressions pass. No deliberate hostile was created; defense/combat safety also relies on the existing automated coverage.

Controller progress rose from 122,899 at 2,243,310 to 131,382 at 2,244,277. A Scout was traveling toward W6N5 at 2,244,129, with fresh scans of W7N3, W7N4, W6N4, W6N3, W5N3 and the home room after sampler start. Remote accounting recorded 2,370 harvested and 146 delivered energy in ticks 2,243,750-2,243,999, followed by additional deliveries. Spawn output showed replacements and new workers after release. No recorded exceptions appeared at the retained checkpoints or final 2,244,277 check. This supports continued operation, without claiming remote profitability, uninterrupted construction or every combat scenario.

Temporary heap profiling hooks were removed at 2,244,394. At 2,244,458 the normal loop was restored, nested timer wrappers were absent, the release build was still executing, controller progress was 132,631 and no recorded errors were present. Normal runtime telemetry remains enabled.

## Remaining scope

Memory footprint/parse cost, economy forecasting, spawn planning and per-creep work remain the main avenues for further measurement. Removing old planners or compressing persistent routes needs a separate compatibility/migration design; durable intelligence was preserved. No new planners, population cuts, disabled features, longer decision intervals or blanket Memory purge were introduced. The 676-tick windows capture recurring short-period spikes but do not cover every long-period task in both windows. Multi-room scalability and active siege combat cannot be certified from this single-colony run.
