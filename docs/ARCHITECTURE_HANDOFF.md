# Sushi architecture handoff

## Operational audit: container ownership and NPC safety

Stationed local and remote Extractors can now transfer existing cargo and harvest in the same tick while their CARRY still has space. The existing unload helper is attempted near the next full-store boundary, avoiding the old mandatory unload-only tick without introducing movement or another job owner. Full or missing sinks retain the existing full-store transfer/drop/bootstrap behavior. `test/extractor-throughput.js` uses start-of-tick cargo/capacity semantics; its idealized output gain is not a live throughput or CPU benchmark.

The November 10 operational audit keeps `Planner.Brain` and `utility` in their existing roles. The room planner now adopts built source/controller containers and pending container sites, retaining a saved station when duplicates already exist. Adoption records an existing site without passing it through the new-site predicate. Construction release also checks for infrastructure serving the same source or controller, so a persisted plan cannot add a second container after utility has placed one elsewhere. Existing duplicate structures and sites are preserved. This does not migrate remote stations or remove their fixed-route authority.

`Combat.ThreatLedger` and the remote planner's safety fallback retain core observations as optional plain `Memory.rooms[room].invaderCore = {id, level, observedAt}`. The ledger uses the tick structure index; the planner's existing per-tick route snapshot shares its fallback scan. Without vision, a remembered core blocks civilian routes and requests scouting; only a visible observation without a core clears the record. The threat snapshot also carries `invaderCore`; a remote installation suppresses ordinary defense targets and aborts existing remote-defense operations, preventing stronghold defenders from bypassing clearing restrictions. Owned-room defense remains available. Existing route invalidation, retreat, ownership, and economy gates retain their owners.

Automatic core/stronghold clearing is deliberately unavailable. The previous assessment derived desired DPS/healing from enemy strength, then treated those desired values as a viable force; its WORK breacher could not dismantle the core. Discovery now reports lesser cores separately from stronger/unknown strongholds without creating attack operations. `Combat.Operations` rejects core clearing, checks deployment/invulnerability, removes executable clearing demands, and aborts legacy missions through existing squad retreat handling. Disabled independent CoreBreakers return home. Ordinary NPC-creep defense and manual player operations retain their existing policy. A tested lesser-core attacker and a force-readiness-based siege system remain future work, not supported capabilities.

Validation adds container-policy, NPC-safety, and logistics-reservation suites to `npm run validate`. These cover construction-site adoption, stale-plan release, persisted core safety after reset/vision loss, legacy clearing cancellation, courier death/target loss, shared delivery capacity and spawn-refill preemption. Live measurements and deployment evidence belong in `docs/OPERATIONAL-AUDIT-2026-11-10.md`.

The November 8 changes below describe remote planning cadence and the preceding verified deployment. General tick order and subsystem architecture remain documented in [`HIVEMIND.md`](../HIVEMIND.md).

## Stationary work, light renewal, and pixels

### Productive remote hauling and CPU admission

The ordinary capacity ceiling remains 55/65/78/83% of baseline according to bucket health. A narrowly evidenced remote Freighter may use a separate delivery margin, capped at 90% projected baseline CPU and requiring bucket >=6000, fresh completed-tick CPU, 20 ticks after reload, a noncritical current CPU mode, a healthy local harvest/hauling floor, a lasting Foreman, and no known home/eligible-source threat. `Economy.productiveRemoteHauling()` requires physically stationed, movable remote miners that will last beyond production/travel, known operational trip geometry and fresh unreserved source energy. Queued miners and selected portfolios alone do not qualify. The final body is capped to the recurring production deficit after healthy existing haulers; backlog catch-up cannot inflate this allowance. Another queued/spawning remote hauler prevents duplicate relief. Energy reserves, spawn load, role limits and the hard population cap still apply. Config `capacity.remoteHaulRelief=false` disables it; `remoteHaulReliefCeiling` can tighten, but cannot raise, the 90% ceiling.

Capacity reserves role CPU for spawning bodies, accepted intents not yet visible, and the first 30 ticks of newborns while the EMA settles, deduplicated by name. A relief candidate reserves at least 0.5 additional CPU. Successful relief births retain bounded `remoteHaulRelief: {spawnedAt, projectedCpu, ceiling}` metadata for live verification; that record is evidence, never an admission authority. Active Artificer capacity classification follows its current work category rather than a stale emergency birth label; incoming critical workers keep their requested classification. Existing workers are not forcibly removed or reassigned.

The same bounded margin may restore one previously productive remote source when remote mining has stopped entirely. `supportedRemoteRestart()` requires prior mining and delivery within 1500 ticks, safe ownership intel no older than 500 ticks (or a 25-tick stock observation when no timed controller record exists), an active safe route, no other active/spawning/queued remote miner, and enough existing healthy remote CARRY for the complete proposed output. Restarting mining creates new energy, so it does not require a current stockpile; delivery relief still requires fresh unreserved stock. It cannot finance a new support fleet or a new remote portfolio. Successful births retain `remoteRestart` CPU evidence. Friendly reservations update the production ceiling immediately from effective reservation intel; hauling and restart admission do not wait for a later portfolio rescore. A full-source local miner also receives a named lifetime replacement when spare seats exist, keeping planning and admission deadlines aligned.

Role CPU samples with timestamps older than 500 ticks, or in the future after a rollback, use the existing 0.2-CPU fallback plus traffic overhead until fresh measurement arrives. This prevents an absent Scout's old expensive workload from permanently blocking the visibility needed for remote recovery. Fresh samples and conservative untimed legacy samples remain honored.

Local Extractors now consider an unreserved second built source container before ordinary side seats, preserving the primary incumbent and the full-WORK admission guard. That guard only treats an active, physically stationed full-source miner with completed handoff as covering the source; spawning or staged successors must not displace productive supplemental miners. Offloading only transfers to a store reachable from the mining tile; otherwise the miner drops for haulers. Emergency self-delivery remains separate. This prevents normal offloading from repeatedly walking out of harvest range.

Techs with energy already in upgrade range can resume work without first topping off. A tile within upgrade range and adjacent to a stocked controller container is protected through the existing traffic lock. If that station occupies a road, the Tech can make one adjacent step onto a free off-road tile that still supports both actions. Terrain, structures, construction sites, resource tiles, creep occupancy and same-tick Tech reservations are checked through the current index without path searches; an off-road worker immediately keeps its tile. Empty fuel or changed economic permission releases the lock; ordinary movement remains available. A loaded policy-paused Tech uses `fillBaseEnergy()` to serve actual spawn/extension/tower deficits, without the Foreman helper's idle-at-spawn fallback. A full base therefore does not trigger a pointless parking trip. Controller fuel selection uses the existing tick structure index rather than repeated path searches. No standing-location Memory or second traffic system was added.

The light/emergency spawn pass reevaluates current Freighter capability and renewal every five ticks. Remote maintenance uses the current miner-committed Economy target and existing route geometry, so ordinary recovery remains available if a consolidation deadline has passed. Selecting an unstaffed remote source alone produces no hauling demand. This keeps CPU-skipped full planning from starving a worker-saving forecast. It reuses Economy, the same request producer, admission policy and queue, and does not request new remote miners or routes. `FREIGHTER_RENEWAL_PLANNED` and `FREIGHTER_RENEWAL_STARTED` events distinguish forecasts from actual successors; existing predecessor records continue to fence natural expiry and reused names.

Capacity admission now uses Economy's revalidated physical hauling-shortfall deadline for renewal, including when excess capacity covers an earlier named predecessor's expiry. Ordinary worker replacements retain their own deadline rules. This avoids invalidating an otherwise feasible larger hauling body just because a redundant predecessor expires first.

`Harvest.Planning.agingConsolidation()` extends the existing source replacement flow to fragmented local miners. At an aging worker's normal replacement boundary, a fully funded body can cover one source's entire WORK target if its cost is no higher than the cohort's future replacement cost and it will remain healthy after the youngest peer expires. The replacement is already needed; its younger peers do not add extra headcount compared with spawning a small body. Charging their whole overlap again would perpetuate staggered small miners. It requires stationed movable miners and a viable handoff deadline, remains source-local, and does not inflate the source target. The request's optional `minerConsolidation` forecast is revalidated through Economy and Policy; loss of funding/peers falls back to ordinary affordable recovery. The named incumbent uses the existing safe handoff, and younger peers are never manually removed by the forecast. The light pass also services endangered local source WORK from the current snapshot every five ticks.

Pixel generation runs after colony actions and diagnostics, before final telemetry. The usual check is a bucket comparison with no config, CPU measurement, Memory writes or room scans. Only a full bucket reaches the policy checks: explicit enabled/cadence settings, 20 ticks after reload, fresh rolling CPU below 83% of baseline, current work below 90%, stable local harvesting/hauling, and no home-room threat. Failed API calls back off 100 ticks. A success consumes the engine's pixel CPU cost, so the following low-bucket period is expected. Bounded attempt/success telemetry lives at `Memory.hive.telemetry.pixels`; `Sushi.debug.pixels()` reads current and last attempt information without a dependency from Diagnostics back to the tick runner. Enabling this policy edits only the requested `Memory.config.pixels` fields; account/server settings remain unchanged.

## Scout planning and deployment ownership

Scout observations still refresh controller and danger information on every visit. `Planner.Remote.generateRemotePlan()` now shares the existing 75-tick heavy-planning interval across Scout and scheduled callers, keyed by home/remote room. `remotePlanner.remotes[name].lastPlanAttemptAt` also backs off failed route searches and survives a module reset; a future timestamp is ignored after tick rollback. Optional route generation uses the existing Scheduler's live and rolling CPU pressure guards. Ownership and danger checks precede the cooldown. Movement, route invalidation/rebuilding, remote assignments, and the existing scheduled planner retain their owners. Deferred discovery resumes when planning CPU is available; no population restriction was added.

The private-server Git checkout owns development; the official folder receives validated root runtime modules through `tools/deploy-runtime.js`. Hash checks fence source/target drift, every release keeps a recoverable runtime backup, and `Runtime.Build.js` exposes the source fingerprint through `Sushi.debug.build()` without per-tick hashing or Memory writes. See [`DEPLOYMENT.md`](DEPLOYMENT.md) for validation, copy, server receipt, and rollback checks.

## Freighter replacement flow

`HiveMind.Economy` continues to own production-based local/remote hauling targets and live CARRY coverage. `spawn.request.manager` remains the request producer; `Spawn.Arbiter`, `Spawn.Policy`, `HiveMind.Capacity`, and `spawn.manager` retain admission and execution ownership. Pickup, delivery, Traveler, and traffic ownership are unchanged.

`Freighter.Renewal` is a forecasting helper used by Economy. It performs no creep actions, queue writes, or demand inflation. Instead of replacing each tiny retirement deficit independently, it examines nearby natural expiries and proposes one body covering the required capacity after that cohort expires. Local and remote assignments are evaluated separately; explicit transport workers do not join either cohort.

1. The producer refreshes the current commitment ledger, then asks Economy for a local renewal before optional remote work. Without a valid cohort it uses ordinary deficit requests.
2. The helper reads physical, movable CARRY, known expiry times, existing successor claims, spawning bodies, accepted intents, and unexpired requests from the existing indexes. Ordinary healthy coverage and actual physical capacity are deliberately distinct: aging workers keep serving until death.
3. Lookahead is the maximum useful body's spawn time plus two modeled haul trips and a 20-tick refill allowance. A cohort needs at least two predecessors and a body of at least two CARRY. The body must cover its forecast deficit completely, fit current active spawning capacity and spendable energy, and have no greater replacement energy cost than its predecessors. Expected lifetime after overlap must justify the worker reduction. At most 50 predecessor records are considered per proposal to bound metadata and computation; this is not a population target.
4. Earliest physical CARRY shortfall determines `needBy`. Earlier expiries already covered by excess (including a born ordinary successor) are excluded from predecessor claims and worker-saving credit. Revalidation applies the same filter, preventing a redundant old worker from capturing a later peer in a false consolidation. A forecast starts only when that real shortfall enters the existing replacement horizon. Younger fragments may join the already-needed successor if the same body-cost and lifetime-payback checks pass; the successor must remain healthy after the final claimed expiry. This avoids stranding fragmented capacity solely because peers expire outside a narrow trip-based age window. Busy spawns, earlier/equal-priority queued production, a full haul trip, and a ten-tick arrival margin must fit before the first shortfall. Full and light planning use the same minimum local maintenance priority, also at least one step above the corresponding hauling request; forecast and execution use that exact priority. Lower-priority work still reserves its economic budget, but does not add a false spawn delay. Calls without a known priority retain the conservative all-queue estimate. Remote renewal requires known, operational trip geometry and a covered local hauling floor. No pathfinding is added.
5. Economy revalidates the named cohort and future deficit at admission and execution. A valid renewal can use the worker-saving replacement allowance through soft CPU/population/role guards. Energy reserves, spawn-load limits, queue policy, and the hard population safety cap remain enforced. This replacement allowance supports critical CPU recovery; it does not promise zero temporary CPU cost during overlap.
6. Execution applies the renewed minimum CARRY capability to the affordable-body preview. Temporary low energy cannot silently turn the combined request into another one-CARRY body. If the cohort, income, route, funding window, demand, or deadline becomes unsuitable, the request becomes obsolete or falls back to ordinary recovery with no retained cohort claims. Generic spawn-policy disabling does not disable the capability guarantee.
7. Predecessors keep collecting/delivering normally until natural expiry. No retirement, recycling, suicide, reassignment, or forced cargo drop is introduced. Once a successor exists, its claims prevent another renewal from selecting the same old generation. Claims expire with the old workers, and damaged/dead successors release them.

Ordinary Freighter replacement lead now includes body production, a full modeled haul trip, and the existing margin. Coverage, Economy snapshots, and local admission use that same travel basis; remote lead uses operational route geometry when available. This allows recovery bodies time to complete a delivery before outgoing capacity expires.

## Optional Memory fields

| Owner | Fields | Lifetime |
| --- | --- | --- |
| Spawn request | `freighterRenewal: { assignment, plannedAt, predecessors, needBy, through }`, `replacementFor` | Existing persistent queue; discarded on completion, obsolescence, or recovery fallback. |
| Successor creep | `freighterPredecessors: [{ name, deathAt }]` | Copied through ordinary spawn Memory. `role.Freighter` prunes after each predecessor expires or changes generation; damaged successors release claims. |
| Admission/preview | `missingCarry`, `minimumCarryParts`, validated predecessor list | Derived per evaluation; cached previews include minimum CARRY in their signature. |

`deathAt === Game.time + predecessor.ticksToLive` fences reused names. Future `plannedAt` values fail closed after a tick rollback. Fields are optional and need no schema migration or live Memory edit.

`Sushi.debug.room(name).current.logistics.renewals` exposes queued forecasts. Individual `current.freighters` rows expose predecessor records for live successors. Existing spawn admission reasons identify consolidation; flow/cargo/CPU diagnostics retain their current meaning.

## Other worker replacement claims

`Spawn.Context.replacementClaims()` also fences ordinary Tech/Artificer replacement allowances after a successful spawn leaves the queue. Successful successors retain optional `workerPredecessors: [{name, deathAt}]` and `workerReplacementWork` in creep Memory. Normalization, capacity admission and the low-CPU Tech maintenance producer exclude already-claimed old generations. Physical/spawning creeps and accepted intents share the claim lookup; no separate reservation controller is added. Claims cease to apply after predecessor expiry/name reuse, successor loss or insufficient active successor WORK; Artificer claims also require the same work category. Own queued requests are excluded on revalidation. This prevents one expiring worker repeatedly funding small successors through the CPU-neutral allowance.

## Remote hauling commitments

Remote stockpile overflow keeps `remoteDeliveryRoom` and `remoteDeliverySourceId` through the drop intent. On the following tick, the existing cargo-delta reconciliation records `haul.lastDeliveryAt` before normal empty-worker cleanup. An accepted drop alone cannot establish delivery evidence.

`HiveMind.Economy.remoteHaulRequirement` caps recurring remote production by movable, active remote Extractor WORK plus queued/spawning/accepted miner commitments for the same home and source. Selecting a source in the remote portfolio alone does not justify recurring haulers. The planner, ordinary admission and renewal forecast share this calculation. Fresh unreserved backlog still permits bounded collection demand; stale backlog does not promise continuing production. Physical miner totals use the existing per-tick index; queues and accepted intents are read again so same-tick commitments remain visible without pathfinding or repeated empire scans.

## Validation and limits

Run `npm run validate`: build identity generation, focused renewal and remote-planning suites, deployment safeguards, module-graph and movement-ownership audits. Package scripts now reference present tests; the earlier cleanup removed the legacy test collection, so historical larger pass counts do not describe today's suite.

The 500-tick models reduce six one-CARRY workers to one hauler, and twelve to two, without a modeled delivery-capacity gap. Funding loss, critical CPU, route closure, damaged parts, queue blocking, rollback, reused names, and live cargo preservation have separate regressions. These are automated decision/capacity models, not engine pathing or live performance measurements.

Trip geometry and throughput remain estimates. Actual congestion, attacks, room topology, changed sinks, or starvation can invalidate readiness assumptions. Sparse expiries or insufficient funding can still require small recovery bodies; continuity takes priority over consolidation. Population falls as predecessors expire and can temporarily rise while successors come online. Renewal was first deployed to official shard3 on November 8; server receipt is recorded in [the live engineering report](LIVE-ENGINEERING-2026-11-08.md).

For ongoing live verification, inspect queued `current.logistics.renewals`, successor predecessor records, selected spawn bodies, and matched-worker delivery deltas using `Sushi.debug.room("W39S47")`. Observe several trips and the old cohort's natural expiry. Confirm that healthy plus incoming capacity remains adequate, predecessor cargo continues moving, and headcount falls after overlap. Compare `Sushi.debug.cpu()` rolling usage and bucket trend over a creep lifetime; the automated capacity models do not establish a live CPU saving.
