# Sushi deployment

The private-server directory (`scripts/192_168_0_217___21025/Sushi`) is the authoritative Git checkout. The official folder (`scripts/screeps.com/Sushi`) is a runtime deployment target, not a second development checkout. Make changes only in the authoritative checkout.

From that checkout:

1. Run `npm run deploy:plan`. This reviews the target against the current source, ancestor commits, or a previously verified deployment. Unexplained edits and unrelated runtime modules stop the process. It runs `npm run validate`, builds the runtime identity, backs up every currently deployed root JavaScript module, and prints the plan path. Nothing is copied to the target yet.
2. Review the printed changed files and backup location. Run `npm run deploy:apply -- "<absolute plan.json path>"`. Source, target, and backup hashes must still match the plan. Any drift requires review and a fresh plan. The script stages the validated bytes, copies only changed root `.js` modules, writes `Runtime.Build.js` last, then checks the entire runtime inventory byte for byte. Tests, Git metadata, dependencies, documentation, settings, and other files are never copied or deleted. Old development documents already present in the target are left untouched.
3. Inspect the Screeps desktop Script panel: official server, branch Sushi, synchronization/upload status, and the active shard's branch. A local byte match alone is not a successful server deployment.
4. In the official shard3 console run `Sushi.debug.build()`. Its complete `id` and `modules` must match the plan. This is a build marker, not a server-side hash of every uploaded module; combine it with the client upload state, new behavior, and absence of missing-module errors. Then compare `Sushi.debug.room("W39S47")`, `Sushi.debug.cpu()`, and recent events over complete haul trips. Match creep identities and TTLs when comparing flow counters; deaths reset aggregate totals. Console diagnostics also consume CPU, so do not sample every tick.

Plans, full runtime backups, validation logs, and deployment results live under `validation/deployments/` in the authoritative checkout and are ignored by Git. Keep them for recovery. Other evidence and documentation can be committed normally. `Runtime.Build.js` is generated before validation and should accompany source changes; it hashes normalized runtime source excluding itself. It adds no per-tick hashing, network calls, or Memory fields. `Sushi.debug.build()` reads the small module on demand.

If a local copy fails after writing begins, the script restores all backed-up modules and reports the failure. If the server becomes unstable after a successful copy, run `npm run deploy:restore -- "<absolute plan.json path>"`, inspect client upload status, and verify the previous behavior. Restore overwrites only the files in that backup; newly added modules remain present and unreachable from the old runtime. No files or live Memory are deleted. Review any subsequent source or target edits before invoking a manual restore.

The Script panel's local synchronization/upload choice is part of the existing workflow. Do not change server/account settings or edit `.sync` as a deployment shortcut. If synchronization is unavailable, report the local copy and server receipt separately.
